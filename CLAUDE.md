# 学习乐园 (Learning Center) — standing rules for every change

This app is the learning hub: a subject picker (`src/hub.ts`, rule 30) in front of the subjects. The first subject, 识字, is the complete Learning Chinese app (the sibling repository `LearningChinese`, which must keep working on its own and is never touched from here). Rules 1-29 describe 识字. It records which Chinese characters (汉字) and idioms (成语) the children learned each week. It is modelled on the sibling
project PianistAssistant (same login, same storage idea, same test approach). The final target is an iOS app; the web version comes first.

1. **Languages.** The UI is Chinese / English / French (`src/i18n.ts`, texts in `src/i18n-data.ts`, keyed by the Chinese source text).
   Every new or changed UI text needs an EN and FR entry. `npm run check:i18n` (part of `npm run build`, the deploy workflow and the tests workflow) fails when one is missing.
   The user's own texts (child names, characters, idioms) are marked with the CSS class `user` / `user-title` and are never translated — keep marking them.
   Never add a one-character key to the translation tables for a UI word without the `user` protection being in place.
2. **Always build before pushing:** `npx tsc --noEmit && BASE_PATH=/ npx vite build`.
3. **Web must keep working.** The GitHub Pages site (`/LearningCenter/`) and the iOS app (relative base, `MOBILE=1`) are built from the same code.
   Nothing that only works at one of them (absolute asset paths, server-only features).
4. **Storage.** Data access goes through `src/api.ts` only (`readJson` / `update` / `remove`). `update` is read-modify-write with retry on a
   GitHub 409, so two devices editing at once are merged — keep every write in that shape. Data lives in a PRIVATE repository (never in this public one);
   the login refuses a public data repository.
5. **Data layout** (`src/model.ts`): `kids.json`, `kids/<id>.json` (characters of ONE child — each child learns different ones), `idioms.json` (shared by all children).
   A week is Sunday–Saturday, numbered from the first week entered (`startWeek`). Rules on the data (duplicates, week numbers) live in `model.ts`, not in the screens.
6. **Tests.** End-to-end suites in `tests/` (see `tests/README.md`); `npm run test:e2e` runs them. Every new feature and every fixed bug gets a suite (or a check)
   in the same change, and the test must fail on the old code. New screens must also pass `05-languages-and-layout` (no overflow / clipping / Chinese left over
   in en / fr on a phone and tablets) and be looked at in the screenshots it saves.
7. **Answer the user in Chinese, step by step, and be honest about what could not be tested** (real iPad / iPhone, real children, real GitHub account, speech recognition accuracy).
8. **Every action answers.** Each user action that takes time or changes data shows a message through `toast()` (`src/ui.ts`): `working=true` (spinner) while it runs,
   closed when done, then a result message (or the error). Messages are always in the top band. Cancelling a confirmation must not produce a "done" message.
9. **Automate.** Anything needed on every release (translations check, tests, deploy) belongs in a workflow or script (`.github/workflows/`), not in a to-do list for the user.
10. **Camera.** The login screen scans a sign-in QR code with the camera (`src/scan.ts`); the iOS app will need the camera permission text (`NSCameraUsageDescription`) when it is packaged.
11. **Planned, not built yet** (agreed with the user, see README): speech recognition for the game (only as an optional experiment: single characters read by a child are recognised unreliably, so the adult taps tick / cross), Excel (.xlsx) EXPORT (import is built: `src/importer.ts`, `src/xlsx.ts`), iOS packaging (Capacitor). **Packaging phase (agreed with the user, to start after the current feature batch is finished and the whole suite is green):** native packages for iOS, Android (Capacitor, same code, `MOBILE=1` build) and HarmonyOS NEXT ONLY (the user wants the native HarmonyOS, not Android compatibility: an ArkTS / ArkUI shell with the ArkWeb `Web` component loading the bundled files, a separate HAP / APP package signed through AppGallery Connect), a native bridge module for what a WebView cannot do (print -> PDF -> share sheet, file download / share for MIDI and DJ recordings, file picker, camera permission text, Android back key, orientation lock, speech), simulator / emulator smoke tests in GitHub Actions (iOS simulator on a macOS runner, Android emulator on Linux, a WebKit-engine run of the web suites; HarmonyOS only by a manual checklist unless the toolchain can run in CI) and, REQUIRED by the user, a folder `packaging/` whose README gives the DETAILED step-by-step procedure to PUBLISH and GO LIVE for every target (web release and rollback, version numbers, signing keys and CI secrets, TestFlight / App Store, APK / AAB / Google Play and the Chinese Android stores, HarmonyOS AppGallery, store listing texts (user decision: the app is listed as a general education tool for parents and teachers, NOT in the Kids / Families categories; the age rating still follows the real content and the store texts must not mislead), a privacy policy (the app collects nothing itself: the data is on the device or in the user's own private GitHub repository), app filing / 备案 requirements in China, a pre-release checklist, how to test on a real device).
12. **One repository per app.** The login refuses a repository that holds another app's data (the piano app's `scores/` `inbox/` `pdfs/`). There are no accounts in this app: a token is just a GitHub key, and the data goes to the repository typed on the login screen.
13. **Both sides equal.** Content must be centred: equal space left and right on every screen size (iPhone, iPad both ways, desktop). `11-centering-devices` measures it on 11 emulated screens; a new screen or element gets a check there. Screens are looked at as screenshots, not only measured.
14. **Week page.** It opens on the week that contains today. The left arrow goes back freely to the first week that has characters; the right arrow only as far as NEXT week (to prepare it). A week has 10 characters: below 10 a small + completes it, at 10 there is no +; an empty week shows a big + in the middle. No big button.
15. **Where things live.** The home screen is the list of children (and, when there are none yet, one big + in the middle); below the list follows a SHARED area (rule 55: for now the card "PK认字"). Adding / renaming / changing the picture of / deleting a child and the Excel import are in Settings (the gear on the home screen); a child's own page has no menu. Idioms are shared by every child: the week page has a "成语故事" button under the characters -> ONE list (`#/idioms`, by week, "＋ 添加成语" adds) -> tap one -> its story page (`#/idiom/<name>`: the idiom in 田字格 cells with pinyin + a story the adult types, saved in `idioms.json` as `stories`; a tap in the left / right QUARTER of the screen (the middle half does nothing) or a swipe goes to the previous / next story of the list it was opened from, "2 / 6" shows where you are, `history.replaceState` keeps "back" = the list; the story is edited with a small faint pencil in the top right corner that opens the editor only on a DOUBLE tap (`doubleTap`, Enter on the keyboard): the page is for the child to read, no big edit button). Idioms are not shown anywhere else; `20-idioms` tests it.
16. **Pictures.** A child's picture is `animal:<name>` (12 drawn animals in `src/art.ts`) or a small square JPEG data URL from the photo library / camera (`src/photo.ts`), stored in `kids.json`. Every place that shows one is size-checked (`12-children-settings-avatar`).
17. **App icon.** One master drawing, `assets/icon/icon.svg` (drawn from scratch in code: no third-party artwork); `npm run icons` makes every size (App Store 1024 px without transparency, apple-touch-icon, manifest icons, favicon). `15-app-icon` checks the sizes, no alpha channel, the iOS corner cut and that the files are in sync with the master — after editing the master run `npm run icons` and commit the PNGs.
18. **Child picture.** On a child's own page the picture opens the picture-and-colour window by a DOUBLE tap (no badge on it; Enter on the keyboard); Settings opens the same window with one tap.
19. **Google Sheets sync** is a script that lives in the user's sheet (`docs/google-sheet-sync/sync.gs`). The user's sheet has its own automation (A = week label, L = running total, duplicate colouring on B..K), so the script touches ONLY single cells of B..K in the right child's tab / week row: it FILLS empty cells, and CLEARS a cell only when the app deleted that character since the last sync (a record of what the app had is kept in the script properties) AND the cell still holds exactly that character; what the user typed by hand and the app never had is never cleared. Safety: no data from GitHub for a child = nothing cleared; more than 30 clears at once = nothing cleared (setting MAX_DELETES). It never overwrites, reformats or touches A / L / formulas (audited by `16-google-sheet-sync`), reads the data repository with a READ-ONLY token and never writes to GitHub. It runs by timers on Saturday and Sunday evening (SYNC_DAYS / SYNC_HOUR), not every few minutes; enabling it first deletes every older `syncAuto` timer, so an old every-10-minutes timer is replaced. The files are in a public repository: no personal data, no token. The test uses a pretend sheet — it cannot prove the real Google authorisation / timer; say so.
20. **The game** (child page -> "Game" tab). ONE shared game for every child: `src/game.ts` (rules, pure, no child in it) + `src/gameui.ts` (screen); only the characters differ (queue built from the selected child's data) and the progress is saved under that child (`kids/<id>.review.json`, removed with the child). Spaced repetition by boxes (1, 3, 7, 14, 30 days); all of this week's characters + due earlier ones (max 10), shuffled; countdown default 5 s (3 / 5 / 8 / 10 / 15 in Settings; the lobby only says "Ready?" + Start); time out = wrong; wrong ones come back (max 4 rounds). The ring is thin and burns away, its colour moves smoothly green -> red. `18-game` tests rules (Node) and screen (a clock the test moves) on 7 screen sizes.
21. **Wording.** What is in a child's list is "已入库" (recorded), not "已学" (learned): putting a character in the list does not mean the child has learned it. Use "已入库" / "Recorded" / "Enregistrés" for the tab, the count, the duplicate messages.
22. **Light only.** No dark mode, on purpose (children learn characters in a bright place; one colour scheme for everybody). `index.html` and `:root` declare `only light` so phones that darken web pages by themselves leave the app alone; never add `prefers-color-scheme: dark` rules. `19-light-only` checks it.
23. **Practice sheet (字帖).** The week page has a "字帖" button -> `#/sheet/<kid>` (`src/sheet.ts`): per character the pinyin, the stroke count, the strokes one by one in writing order and a row of 12 田字格 cells (character, traced copies, empty cells); the printout is the browser's own (`window.print`, "Save as PDF"), ten characters on one A4 page. The stroke data is Make Me a Hanzi via `hanzi-writer-data` (Arphic Public License): `scripts/make-strokes.mjs` writes `public/strokes/*.json` (6763 everyday characters, ~15 MB, committed) and the license text; it ships INSIDE the app (works offline, nothing is fetched from elsewhere, no tracking: also fine for the local-only store builds) and the license notice is in Settings ("致谢"). Do not remove the notice or `public/strokes/ARPHICPL.TXT`. **iOS app:** `window.print()` does nothing in a WKWebView, so when the app is packaged the "打印 / 保存为 PDF" button needs a native path (make the PDF, then the share sheet) - not built yet. `21-practice-sheet` tests it, including a real PDF made by the browser.
24. **Idiom library.** The user's 成语 tab (A = idiom, B = tick box = already used, C = count made by the sheet, no dates) is imported once from Settings (`isPoolSheet` / `parsePool` / `applyPool` in `src/importer.ts`): the whole list goes to `idioms.json` as `pool` (sheet order), importing RESETS the weeks of idioms (the sheet wins, the preview warns first): an idiom with a week in column D ("第4周-2026-11-15", written by the sync script) goes back to exactly that week, the other TICKED idioms are given weeks in sheet order, 6 a week (`M.IDIOMS_PER_WEEK`), over the weeks that have started (every week with characters up to this week) + NEXT week; the rest stays in the pool; stories are kept. When the app loads its data (`loadShared` -> `autoPickIdioms`) NEXT week is topped up to 6 with random unused pool idioms (read-modify-write through `api.update`, so two devices never pick twice; nothing without a pool; a toast says it). The sync script (`syncIdioms_`) only ever TICKS B for idioms that have a week, never un-ticks, never touches A / C. `22-idiom-pool` and `16-google-sheet-sync` test it; a real Google account / timer can not be tested.
25. **Idioms typed by hand** (the "＋ 添加成语" window): checked as you type (`M.classifyIdioms`): an idiom that already has a week (in ANY week) is refused with its week named and Save is off; one that is in the library is just picked for the week; one that is not in the library is added to the week AND to the end of the library (`M.addIdiomsByHand`). The sync script (`syncIdioms_`) then appends library / week idioms that are missing from column A of the sheet's 成语 tab below the last idiom (with a tick box in B, ticked when it has a week; at most `MAX_IDIOM_ADDS` = 30 at once), ticks B for idioms with a week and writes the week into D (only into an empty D cell or one holding an old week label with another week; anything else the user wrote there stays); it never changes an existing A / C cell and never un-ticks. The user's protection of column A only matters for the Google account that authorised the script - not testable here, say so. `22-idiom-pool`, `20-idioms` and `16-google-sheet-sync` test it.
26. **Story printout.** The idiom page of a week has a "打印故事" button -> `#/stories` (`src/storysheet.ts`): THREE stories per A4 page (180 x 266 mm inside the 15 mm margins), 14 pt type, each story under its idiom written as a PLAIN line of the same size (no 田字格, no pinyin, no decoration); the week's six stories = two pages = one sheet printed on both sides. A story too long for its third is set smaller (down to 11 pt) and named; one still too long is marked / warned (the printout would cut it); the page states how many characters (no punctuation) fit at 14 pt (measured from the layout, about 185). Printing is the browser's own (`window.print`; same iOS caveat as the practice sheet: a WKWebView needs a native PDF path). `23-story-sheet` tests it incl. real 2-page PDFs.
27. **Built-in story library.** `public/stories.json` ({stories: {idiom: text}}): simple idiom stories, AT MOST 150 characters each (punctuation counted), written only with characters of GB2312 level 1 (3755 everyday characters: the closest offline list to what primary-school children know), plain text, one paragraph. Settings -> "成语故事库" -> "把自带的故事填进成语" fills the idioms of the app (library or weeks) that have no story yet (`M.fillBuiltInStories`); a story the user wrote is never replaced. New stories must keep these rules; `24-story-library` checks length, characters and the button.
28. **Stories in the sheet (column E).** The 成语 tab's column E holds the story of the idiom. Import (`parsePool` -> `applyPool`) puts a story into the app only where the app has NONE (a story written / edited in the app always wins, `storiesKept` is counted in the preview); the sync script (`idiomStoryWrites_`) makes column E FOLLOW THE APP (the app is the master, the sheet is the backup): an empty E cell is filled, a cell with another text is rewritten with the app's story (at most `MAX_STORY_OVERWRITES` = 50 rewrites of non-empty cells at once, else only the empty ones are filled and the status tab says so); an idiom the app has no story for keeps its E cell (never cleared); the same text is not written again. Stories written FOR the user go into column E of his sheet (not into the public repo): check them with `node scripts/check-stories.mjs file.tsv` (max 150 characters with punctuation, everyday characters only, plain text). `22-idiom-pool` and `16-google-sheet-sync` test it.
29. **Practice sheet for a child who writes fewer characters than he reads** (Leo). On the sheet page "字帖设置" (`sheetSetupDialog`): per child (device setting `settings.sheetWrite[kidId]` = `{on, chars}`) the grown-up types the characters to WRITE: ONE text field that accepts only Chinese characters and at most 10 (anything else is dropped on the spot, `M.parseChars`; the count "n / 10" is the only text; no explaining paragraph). With the option on the sheet is made for them and THIS week's characters (left of the frame) and LAST week's (right of it) are printed beside the rows in RANDOM order, WITHOUT boxes, as big as the characters in the cells (10.5 mm), at the height of the writing cells, just outside the frame (`buildSheet(chars, {left, right})`); to make room the frame is 170 mm wide instead of 178.5 and that sheet's page has 6 mm instead of 15 at the sides (a `<style id="sheet-read-page">` is added while it is shown and removed in `route()`). Every sheet is a FULL page: the ten rows share the whole height (`.sheet` is a grid of 10 rows, 266 mm high when printed, paper-shaped on the screen so the preview is what is printed). The window comes up AT ONCE the first time the sheet button of a child's week page is pressed (nothing remembered yet = the option is ON; cancelling decides nothing, no message) and from then on every time while the option is on (remembered per child, filled in with the last characters); only when the grown-up switches it off there does the sheet button go straight to the usual sheet. One A4 page; `25-sheet-write-chars` tests it incl. real PDFs.
30. **Subject picker (学习乐园).** Signing in ends at `#/` = the picker (`src/hub.ts`: `SUBJECTS`, `hubGrid`, `choose`, `reveal`, `soonPage`): four BIG cartoon cards (识字 / 数学 / 英语 / 科学, artwork drawn in code as inline SVG, no image files, only digits / Latin letters inside the pictures), 2 x 2 on phones and portrait, 4 in a row on wide landscape screens, equal space left and right. A card tap = squash + ring + sparkles (`.fx-layer`), then a curtain in the card's colour grows from the tap with the subject's picture (`#curtain`), `show()` calls `reveal()` which lifts it and grows the new screen in (`.enter-zoom`); with `prefers-reduced-motion` all of that is skipped and the route opens at once. A double tap opens only one subject (`busy`). Routes: `#/` picker, `#/chinese` = the former home screen of 识字 (list of children; its back button returns to the picker), `#/subject/<id>` = the "coming soon" page of a subject that is not built yet (`ready: false`; building one = give it its own route / screens, set `ready: true`, add its suite). **识字 must stay what it was**: every route, text and behaviour of rules 1-29 is unchanged below `#/chinese` (only the addresses `#/` -> `#/chinese` moved; the child pages, idioms, sheets, game and Settings keep their addresses). Settings is shared: its "完成" returns to where the gear was tapped (`settingsBack`). Storage keys (`learn.*`) are the same as in the standalone app on purpose: same origin = same sign-in; never change their format without the standalone app in mind. New subjects store their data under their own file names in the same private repository (never inside `kids.json` / `kids/<id>.json`). `28-subject-hub` tests the picker, the effects, the routes and EN / FR / small screens; the test harness signs in and then taps the 识字 card (`toChinese`).
31. **Grade (年级) belongs to each CHILD.** Nothing is asked on the subject picker. The grade is asked ONCE per child, the first time that child is opened in a subject that needs it (English: `renderKid` -> `pickKidGrade` in `src/gradeui.ts`; cancelling goes back to the list and saves nothing), and can be changed any time in Settings -> manage mode -> Children -> the 年级 button of that child (and from the grade link on the child's English page). No default grade is ever assumed. Remembered on this device (`src/profile.ts`, key `learn.profile.v1`, `kids[<id>] = {grade, setOn}`), used by every subject. The grade of today is calculated (`advance`): +1 on every 1 September (`schoolYear`), at most 初三 (9), never down. Not synced between devices yet (a `profile.json` in the data repository is the planned way). Tests set grades the way a user does (`harness.cjs` `setGrade`). `29-english-words` tests it.
32. **English words (`#/subject/english`).** Same screens as 识字: list of children (the same children as 识字) -> `#/english/<kid>` with the tabs Game | This week | Recorded (`src/english.ts`). Every week gets exactly 20 NEW words (`W.WEEKLY_WORDS`), picked when this week or next week is first opened (`ensureWeek` -> `W.pickWords` inside `api.update`, so two devices never make two batches; earlier weeks are never made up): from the first word of the child's grade on in the library's order, skipping every recorded word; the words of lower grades follow only when the end is reached. Data: `english/<kid>.json` in the SAME shape as the characters (`weeks[].chars` holds the words, so `game.ts` is shared unchanged) and `english/<kid>.review.json` (memory boxes). The Chinese files (`kids*.json`) are never touched. The game is the 识字 game in "words" mode (`gameui.ts` `words` option): the word as plain text (long words shrink to stay inside the ring), a tap shows the MEANING (not pinyin), a speaker button says the word (`speechSynthesis`, offline, nothing where a device has no voice). **Game queue** (`gameQueue`): ALL of this week's words + `W.REVIEW_WORDS` (10) RANDOM words of the WEEK BEFORE (so 30 questions); when there was no week before, the week is treated as the first week: only its own words. **Recorded tab**: not the whole list, but `W.RECORDED_SAMPLE` (30) random words out of everything recorded, a "换一批" button reshuffles, the total is shown. The library `src/data/english-words.json` (~1565 words, grade 1 first) is built from ECDICT (MIT, https://github.com/skywind3000/ECDICT: the 中考-tagged words, ordered by frequency, function words removed; phonetics, part of speech) plus hand-written theme words for grades 1-9; the grade split is a SAMPLE to be checked against the 2022 curriculum word list; some meanings are the dictionary's first sense (e.g. "just") and need review. It ships inside the app (works offline). The other files in `src/data/` (`curriculum.json` scope by grade, `math-topics.json`, `periodic.json` all 118 elements, `science.json` facts + formulas) are the library for the next subjects, not used by a screen yet.
33. **Math, part 1: mental arithmetic (`#/subject/math`).** Same screens as 识字 / English (`src/math.ts`): children -> `#/math/<kid>` with Game | TODAY | Recorded. **Practice is not memory work, so the topics change EVERY DAY**: a DAY (`weeks[].start` = the date) = 3 TOPICS (2 of the grade + 1 of a lower grade; the old text below says "week": read it as "day"; the game mixes 14 questions of today's topics + 6 of the day before's; earlier days are never made up, the future is not made in advance; a grade change picks today's again; days can be looked at with ‹ ›). A week = 3 TOPICS (knowledge points) of the child's grade (`MM.pickTopics`: the grade's list in order, skipping the ones he had; when fewer than 3 are left the list starts again), made once when this week / next week is opened and kept in `math/<kid>.json` (same shape as the words: `weeks[].chars` = topic ids); changing the child's grade picks them again (`pickKidGrade` handles `english/` and `math/`). **Questions are never stored: they are made on the spot** by one generator per topic (`src/mathgen.ts`, `GEN`, 49 topics = every id of `src/data/math-topics.json`, which lists them per grade): each returns the text, the right answer and `chk`, a JS expression that must be true when the answer is right; `make()` adds three plausible wrong choices (four different choices, the answer among them). A new topic = a generator + its entry in math-topics.json + translations of its question text (every question text with Chinese in it is a template literal known to `check:i18n`); `30-math` makes 1500 questions per topic and checks every answer, the choices and the ranges of the lowest grades — add a range check for a new topic. **The game** (`src/mathui.ts`): NOT the per-question countdown of 识字: ONE TOTAL time (a bar that runs down; the sum of `secOf(topic)` seconds per question, about 5-8 minutes), 20 questions = 14 of this week's topics + 6 of last week's (`MM.gameTopics`; no week before = all 20 from this week), four big choices, the child answers by himself (no grown-up taps), right goes on at once, wrong shows the right answer (green) for a moment, the game ends when the questions are done or the time is up ("时间到！"); the end screen shows the score, the time and a line per topic; leaving asks and saves what was answered. A quick practice (10 questions of one topic) starts from a topic card on the week page. Results: `math/<kid>.review.json` (`MM.applyMath`: right / wrong per topic, last game); the topic cards show the answer rate. The question text is measured AS SHOWN (`fitQuestion` translates first): sentences wrap, expressions stay on one line, both are made smaller when too wide or too tall. **Also built:** (1) 65 topics: besides the arithmetic ones, 7 WORD-PROBLEM topics (`wp1`..`wp7`, Chinese sentences as template literals with translations) and 9 more junior-high ones (`absval power ineq sqrtsimp sqform factor invprop quadvertex arc`); (2) **settings of this device** in the Game tab (`src/mathsettings.ts`, key `learn.math.v1`): the TOTAL time (automatic = the sum of `secOf`, or 3 / 5 / 8 / 10 / 15 minutes) and the way of answering — four choices, or a KEYPAD (`mathui.ts` `press`, also the physical keyboard): only answers that can be typed (whole numbers, decimals, negatives, percents, plain fractions: `typable`) are typed, all other questions are still chosen; a typed answer must equal the stored answer exactly (simplest form); a wrong one shows "正确答案：…"; (3) **errors book**: every wrong question (text, answer, choices) is kept in `math/<kid>.review.json` as `mistakes` (newest first, at most `MM.MAX_MISTAKES` = 50); the Recorded tab shows it with a "重做错题" button (a game of exactly those questions); a right answer takes a question out; (5) **the scratch paper (演草纸, `src/scratchpad.ts`)**: beside the question on a wide / landscape screen, under it on a tall one; a squared sheet to write a sum out with a finger, an Apple Pencil (palms are ignored once a pencil was used) or the mouse; pen in two colours, eraser, undo, clear; cleared for every new question; the button ✎ 演草纸 in the top bar shows / hides it (remembered in `learn.math.v1`); not in the science game; (4) **the choice of topics learns**: when a grade's list has been used up, the new round starts with the topics answered worst (`pickTopics` `acc`). Not built yet: word problems with several steps / pictures, the topics' mastery for the choice INSIDE a round, a printable errors book.
34. **Everything works OFFLINE.** The libraries are part of the program: `src/data/*.json` (English words, curriculum, math topics, periodic table, science facts) are IMPORTED (`import("./data/....json")`, compiled into the build), never `fetch`ed from a path, so they work without network and in a packaged app (iOS, file / capacitor origins). Math questions are made by code. English speech uses the device's own voice. No font, script, image or API of an outside server is used by any screen (the data repository on GitHub is the only network use, and only when the user chose it; "on this device" mode uses none).
